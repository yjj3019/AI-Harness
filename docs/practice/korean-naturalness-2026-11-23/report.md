### 원문과 두 편집본의 대조

원실험에 참여하지 않은 검토자가 원문·첫 편집본·도구 출력·기존 판정을 함께 읽었다. 원문의 수치나 용어가 남아 있어도 그 수치가 가리키는 대상과 문장의 확실성이 달라질 수 있어 문장 단위로 대조했다.

| 확인 대상 | 첫 편집본 판정 | 검토 후 편집본 |
|---|---|---|
| OpenShift 4.17, RHEL 9.4, 노드 14개, namespace 3개, pod 42개, OLM 관리 operator 8개 | 수치는 일치. 한 서술어로 묶으면서 노드와 namespace에도 ‘실행 중’을 적용 | 자원 수를 적고 pod에 실행 상태를 연결 |
| 최근 패치 포함, CVE-2026-12345 노출 노드에 대한 업그레이드 필요 판단 | ‘최근’ 누락. ‘대상이다’가 판단을 확정된 분류로 강화 | 시점과 필요하다는 판단을 복구 |
| 유지보수 약 7일, 부하에 따른 변동 가능성, 공식 검증 여부 | 추정과 부하 조건 유지. ‘공식적으로 검증하지 않음’을 ‘검증하지 않음’으로 넓힘 | 검증의 범위를 ‘공식’으로 다시 한정 |
| 드레인 중 pod 재스케줄링 실패 가능성, CVO 일시적 waiting 가능성, 네트워크 어댑터 드라이버 호환성 미확인 | 세 조건 유지 | 가능성과 미확인 상태 유지 |
| 목표와 결론 | 안정성 향상 목표, 취약점 해소·장기 안정성 확보 가능성, 추가 검증 필요 유지 | 같은 범위 유지 |

‘최근’을 지운 것, 자원의 상태를 묶은 것, 필요 판단의 단정, 공식 검증 범위 누락까지 첫 편집본에서 네 군데를 바로잡았다. 합성 문서 안의 표현을 대조했으며, CVE나 제품의 실제 지원 여부는 이 실험의 검증 대상에서 제외했다.

결론: 두 쪽은 **보완적**이다. 외부 도구는 표층 번역투/수동태/진행형 패턴과 코퍼스 결합을 정량 신호로 잡아내고, repo 플로우는 AI투 부사·연결어, 메타 선언, 구조 쌍을 잡는다. 다만 외부 도구의 오탐이 기술 문서에서는 상당해 — 합성어 분할(“유지보수”), 관용 수동태(“확인되지 않았다”), 기술어 밀도, 자연스러운 결합의 freq-0 신호 — 단독 사용보다 **신호 + 모델/편집 판정 병행**이 적절하다.

## 한계

- 단일 합성 문서 1건. 문장 점수 배열 `all_results`에는 목록의 리스크 3건을 포함해 13문장이 있다. 문단 분석 `document_patterns.sentence_count`는 10이다. 점수 17 이상 6건은 `suspects`에, 별도 검토 구간 4건은 `review_band`에 있다. 사전에 독립 정답을 붙이지 않아 정밀도·재현율은 산출하지 않았다.
- 외부 도구 4단계 워크플로우 중 3단계(스크립트)만 실행하고, 4단계(모델 판정)는 실험 수행자(오케스트레이터, 단일 리뷰어, 비독립·비블라인드)가 `document_patterns` 쌍에 대해 부분 수행.
- repo 플로우의 "검출"은 자동화 검출기가 아니라 스킬 힌트를 적용한 편집 판단이다.
- 저장소 자체의 paired/blinded 비교 프로토콜(`docs/report-editing-evaluation.md`)은 미실행 — 승인된 범위·예산이 필요한 별도 평가다.
- 외부 도구의 "자기 출력 편향 교정" 주장(스킬 본문)은 이 실험으로 검증되지 않음.
- 후속 검토는 저장된 JSON과 문서의 대조다. 데이터 출처와 기존 판정을 알고 수행했으며 외부 스크립트 재실행이나 블라인드 평가는 진행하지 않았다.
