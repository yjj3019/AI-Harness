# 한글 화면과 대시보드 구조도 검증

## 한 화면에 두 지침 적용

합성 과제는 운영 담당자가 점검 결과를 다시 조회하는 화면이다. 이 과제의 브랜드 기준은 남색 버튼, 시스템 글꼴, 단순한 표다. 좁은 화면에서도 버튼 문구와 표 제목을 끝까지 읽고, 키보드로 오류 후 재시도하며, 움직임 감소 환경에서 진행 상태를 읽을 수 있어야 한다.

검토 대상은 두 지침 모두 같은 [화면](review.html)의 `?view=defect` 상태다. 아래는 기준 커밋 `d1e0922`의 지침과 이번 지침을 한 검토자가 같은 결함에 적용한 결과다. `?view=corrected`는 기술적 수정이 동작하는지 확인하는 대조군이다. 두 화면을 서로 다른 스킬로 독립 생성하는 실험은 수행하지 않았다.

| 고정 사례 | 기준 커밋의 지침으로 검토 | 이번 지침으로 검토 |
|---|---|---|
| 긴 한글 제목과 버튼 | 잘림 금지와 여러 너비 검사로 판정 가능 | 긴 한글 버튼과 표 제목을 좁은 화면에서 모두 검사하도록 대상 명시 |
| 탭 포커스와 오류 후 재시도 | 가시 포커스와 키보드 접근으로 결함 판정 가능 | 같은 기준 유지. 역할과 이름으로 버튼을 찾고 Enter와 Space로 실제 조작 |
| 움직임 감소 설정에서 계속 도는 진행 표시 | 시각 QA 목록에는 설정별 정지 확인이 없음 | 일반 설정과 움직임 감소 설정을 바꿔 애니메이션 이름과 상태 텍스트 대조 |
| 남색 버튼과 시스템 글꼴 | 기존 토큰 존중과 별도로 미적 위험 및 서명 요소를 요구함 | 명확한 조회 동작과 기존 브랜드를 근거로 색과 글꼴 유지. 추가 장식은 필요 없음 |

## 브라우저에서 관찰한 결과

Windows에서 Chrome 157.0.8103.80과 Playwright Core 1.64.0-alpha-1790635538000으로 실행했다. 뷰포트마다 같은 버튼을 접근 가능한 이름으로 찾고 Tab으로 이동했다. 네 경우 모두 Enter로 조회해 빈 상태에서 로딩과 오류 텍스트를 확인한 뒤, Space로 재시도해 완료 텍스트를 확인했다.

| 너비와 화면 | 페이지 가로 넘침 | 버튼 내부 넘침 | 키보드 포커스 테두리 | 움직임 감소 중 로딩 표시 |
|---|---:|---:|---|---|
| [320px 결함](defect-320.png) | 224px | 206px | 없음 | 회전 |
| [320px 수정](corrected-320.png) | 0px | 0px | 실선 | 정지 |
| [960px 결함](defect-960.png) | 0px | 0px | 없음 | 회전 |
| [960px 수정](corrected-960.png) | 0px | 0px | 실선 | 정지 |

320px 결함 화면은 표 자체가 오른쪽으로 밀려 제목과 결과 열이 화면 밖으로 나갔고 버튼은 말줄임으로 끝났다. 수정 화면에서는 표 제목과 버튼이 세 줄로 보였다. 네 캡처의 버튼 색은 모두 `#254b75`, 글꼴 지정은 `system-ui, sans-serif`였다. 일반 모션 설정에서는 네 경우 모두 로딩 표시가 회전했다. 측정 단위는 CSS 픽셀이며 [관측값](observations.json)에 원래 값을 남겼다.

## 재현

기존 Node.js, Playwright Core 및 Chromium 호환 브라우저가 있는 환경에서 저장소 루트에서 실행한다. 두 인수는 로컬 설치 경로다.

```text
node docs/practice/design-validation-2026-11-23/render.cjs <playwright-core 경로> <브라우저 실행 파일 경로>
```

검사기는 오프라인 브라우저 컨텍스트에서 폴더의 HTML만 열고, 같은 폴더에 스크린샷과 관측 JSON을 쓴다. 예상 화면은 320×600 및 960×600에서 각각 결함·수정 1장씩, 구조도는 600×640에서 인쇄 CSS 1장이다. 키보드 동작의 네 상태는 DOM과 접근 가능한 버튼 이름으로 검사한다. 실제 모바일 기기의 OS 글꼴·터치, 스크린리더 음성 출력 및 물리적 인쇄 결과는 미검증이다.

## 구조도의 근거

[구조도](dashboard-flow.html)는 Phase 제목의 데이터 흐름을 묘사한다. 입력 일부를 골라 그렸으므로 증거 상태 계산에 사용하는 attestation과 필수 Phase 목록은 도면 범위 밖이다. 제목의 출처를 묻는 그림에 배포 환경, 포트, 네트워크 구간, 외부 시스템 또는 권한 경계를 추정해 넣지 않았다.

| 도면 연결 | 근거가 되는 코드와 판독 방법 |
|---|---|
| PHASES.md → dashboard-status.js | [생성기](../../../scripts/dashboard-status.js)의 `phasesFile`, `definitions`, `phases`가 정의를 읽고 ID와 제목을 추출한다. |
| dashboard-status.js → status.json | 같은 생성기의 `out`, `next`, `writeFileSync`, `renameSync`가 상태 목록을 직렬화하고 변경되었거나 강제 생성할 때 출력 파일을 교체한다. |
| status.json → index.html | [대시보드](../../../dashboard/index.html)의 `fetch('status.json')`과 `render`가 제목이 있는 항목에 ID와 제목을 표시한다. 화살표는 데이터 흐름이므로 브라우저 요청의 방향과 반대다. |

구조도의 화살표와 도형은 HTML·CSS로 직접 작성했다. 글꼴은 운영체제 기본 글꼴을 참조하며 글꼴 파일과 로고를 배포하지 않는다.

[600×640 인쇄 CSS 캡처](dashboard-flow-print.png)에서 노드 4개와 화살표 3개를 확인했다. 일곱 행 모두 글자 크기는 16 CSS px였고, 마지막 노드까지 화면 안에서 읽을 수 있었다.
