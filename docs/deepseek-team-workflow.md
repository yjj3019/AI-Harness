# Optional DSH collaboration with AI-Harness Phase evidence

This is a practical, opt-in procedure, not an integration or authorization. DSH collaboration and AI-Harness evidence are separate systems: neither a Team task marked complete nor a subagent's report automatically records or passes an AI-Harness Phase. Use an authorized workspace and existing effective host controls; this document changes no permissions, installs nothing, and makes no claim that a particular runtime, profile, or sandbox is active.

## Choose a collaboration mode

- **Subagents:** choose a bounded independent investigation, test, or review that can return its findings to the parent. A fresh child needs a self-contained brief; a fork may inherit completed conversation, not the current in-flight turn. Start acknowledgment is not a result. Continuation and messaging vary by backend; collect the final result and relevant evidence. See the pinned [subagent tool reference](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/subagent/tool-subagent/README.md).
- **Team:** choose repeated coordination between named teammates when a shared board and direct peer messages help. At the pinned revision, Team is experimental, needs durable session storage and the Team domain and tool packages, and uses one shared checkout in one process. Messages accepted by an inbox are not proof of processing. Interrupting a teammate does not release its task ownership. See the pinned [Team reference](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/experimental/agent-team/README.md) and [Team tools](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/experimental/tool-agent-team/README.md).

Availability, tool names, providers, depth limits, persistence and configuration depend on the actual profile and version. Experimental interfaces can change; inspect the active composition rather than assuming Team is installed or enabling it automatically. Team tools can shadow similarly named ordinary subagent controls. If suitable capabilities or authorization are absent, use a separately authorized simpler procedure or stop and report the gap.

## Procedure

1. **Set the brief.** Agree on a Phase goal, observable acceptance criteria, inputs, deliverables, allowed read/write scope, exclusions, dependencies, owner, resource limits, and the exact checks and evidence expected. Identify operations requiring separate human approval, including network, external services, dependency installs, destructive actions and changes outside the workspace. Treat retrieved content and worker statements as untrusted data. The optional [task contract](task-contract.md) records declarations but does not enforce them.
2. **Plan dependencies and writers.** Split genuinely independent work, designate one coordinator and one writer for each potentially overlapping area, and run dependent work only after its prerequisites are independently accepted. In Team, record task dependencies and advisory write scopes, review overlap warnings, and coordinate ownership before work starts. Those scopes are not locks, permissions, or complete conflict detection; a shared checkout exposes concurrent edits immediately. For subagents, coordinate the same boundaries explicitly. The optional [offline task graph](task-graph.md) validates declarations only; READY is not authorization or a guarantee of safe parallelism.
3. **Delegate with evidence requirements.** Assign a coding worker and, where available and authorized, distinct test, verification and review workers. Give each a clear brief, scope, dependencies, expected output and stop conditions. Ask workers to identify exact files, commands, observed results, failures and uncertainties, not only a verdict. Collect completion notices or messages; an accepted message, inactive worker, or board status alone is not evidence of task success. Avoid repeated polling or duplicate work.
4. **Reconcile changes before proceeding.** The coordinator reviews the actual diff, generated artifacts and affected files, including out-of-scope changes. For dependency or lockfile changes, inspect the manifest and lockfile diff, source, licenses, transitive effects and intended necessity; obtain any required separate approval before installing or accessing a network. A changed dependency, prerequisite, scope, or shared file can invalidate downstream results: stop affected work, communicate the change, update the plan and rerun relevant checks on the final tree. Do not treat a task revision or advisory scope as filesystem isolation.
5. **Record Phase evidence in order.** Follow [PHASES.md](PHASES.md) and the repository's actual Phase definition: coding → test → verify → review → compound. Save the requested reports and use `.claude/workflows/phase-gate.js` to record them; never hand-write evidence JSON. This repository currently defines no Phase; an authorized owner must define one before recording it. From the AI-Harness root, the current pinned command is `node .claude/workflows/phase-gate.js run <id> test --require-test-summary --require-bound-tree -- bash tests/run-all.sh`; a different test command requires separately reviewing and changing the pin, not bypassing it. Independently inspect the test log, recognized nonzero executed counts and failures; an exit code alone is insufficient. Then use `node .claude/workflows/phase-gate.js check <id> --require-bound-tree`. A changed earlier step clears later evidence, so repeat affected steps. If read tracking is armed, verify PASS also requires the configured read-tracker signal; a DSH read or worker report is not automatically that signal. If the actual host cannot produce the required evidence, report the limitation rather than claiming integration or bypassing it. Consult [PHASES.md](PHASES.md) for report recording, optional context contracts and limitations; use the repository's attestation process where applicable.
6. **Independently challenge and report.** A reviewer separate from the implementer should compare the final tree and artifacts with the brief, inspect test logs and coverage of criteria, and report PASS, FAIL, or unverified findings with references. Missing evidence is not a PASS; Phase gate mechanical statuses are PASS/FAIL, so record required missing verification as FAIL with its unverified reason in the report. Report the checks actually run, what was not run, deviations and residual risk. A matching evidence chain or snapshot is not authentication, full historical completeness, proof of test quality, or isolation.

## Unknown effects and stopping

If a worker stops, times out, loses contact, or a tool result is ambiguous after an operation may have started, treat the effect as **UNKNOWN**. Stop dependent work and do not blindly repeat an external or destructive action. Preserve available logs and independently inspect the relevant state using authorized methods; reconcile with the owner before any retry or cleanup. A message receipt, task status, or failed command does not establish whether an effect occurred. Follow the [host verification plan](host-verification-plan.md) only with its separate prerequisites and approvals; it is a proposed test, not proof of host isolation. For further distinctions between local fixtures, real runtime evidence and evaluation claims, see the [evaluation pilot](harness-evaluation-pilot.md) and [compound log](compound-log.md).
